# Fit checklist

Governed by [`CONSTITUTION.md`](../CONSTITUTION.md) C10. Append-only —
new fit/layout bug → add a row, never delete or renumber existing ones.

Check before shipping any screen/L5-L8 change. A user input reporting a
rendering/layout defect gets matched against this table first: matches a row
→ apply its rule directly. New failure class → fix it, then append a row here
so it isn't rediscovered next time.

| # | Title | Symptom | Rule |
|---|---|---|---|
| 1 | Fixed doesn't stretch | Sidebar/rail leaves dead space below it inside a taller `fill` container | `fixed` boxes never auto-stretch (`.bx-fixed{flex:none}`). Override the size dial's `h`/`w` numeric at the usage site to match the container's actual measured height/width. |
| 2 | Part default ≠ fill | Content panel (card/chart/etc.) doesn't reach the container's right/bottom edge | A part's base `w`/`h` is its demo size, not "fill". When the part should reach the edges of a bigger container, override `w`/`h` to that container's measured inner size — don't assume it grows on its own. |
| 3 | Fixed doesn't clip | Child (text/button/etc.) visually spills past its `fixed` parent's border | `fixed` doesn't clip by default. Measure the child's real rendered box (`getBoundingClientRect`) and confirm it's ≤ the parent's literal `h`/`w`; size the parent to comfortably fit its tallest/widest child instead of shrinking the child. |
| 4 | Minimize size-noise | Screen has many distinct/arbitrarily-measured x or y edge values ("size-noise") | Minimize the count of distinct coordinates. Reuse an existing width/height value across similar elements (one shared card width, not three) instead of picking a new one per element. Prefer a value derived from a documented formula (`root_h - topbar_h - statusbar_h`) over a one-off live measurement. Where an exact fit matters (checklist #1-3), still verify the final number against the live render — a formula can be off by the few px a border/box-sizing eats; correctness beats round numbers. |
| 5 | Bare box can shrink | A row/stack child silently shrinks below its own content's height, content visibly overflowing its own shrunk box | Any box with no size dial (no `fixed`/`fill`/`hug`) gets the plain `.bx` default: `flex-shrink:1` + `min-height:0` (`.bx` base rule strips the usual flex auto-min-size protection). If a sibling's size grows and total content now exceeds a `fixed`/`fill` ancestor's height, THIS child — not the one you resized — silently gets crushed instead of the container scrolling. Give every row/stack child an explicit size dial (`hug` for content-sized, `fixed`/`fill` otherwise); never leave one bare among sized siblings. |
| 6 | Fill the trailing gap | A trailing element should consume whatever space is left after its `hug` siblings, and a hand-computed height/width for it keeps drifting out of sync whenever a sibling changes | Nested BBox must never exceed its parent's BBox (C10) — but don't enforce that by hand-measuring and hardcoding a number. Give the element (and its wrapper, if any) the `fill` size dial instead of `hug`/`fixed`; flex-grow computes the exact remainder itself and stays correct when siblings change. A part's own baked `w`/`h` still needs an explicit override on the *cross* axis (the axis `fill`'s `align-self:stretch` doesn't reach because the base part already sets that dimension) — leave the *main* axis (the one meant to grow) unset so `fill` can grow it. |
| 7 | Row-sizing order | Items placed in a row: how to size them | Runs *before* #4. Default: equal width per item, row spans its full BBox edge-to-edge (first item's left = row's left, last item's right = row's right — same rule as #6, just per-item instead of one trailing filler). If equal division would make any cell too narrow — content wraps/spills, or looks orphaned/floating mid-cell — do NOT force equal width: fall back to each item's own content-fit width, packed from the left. Unequal widths are legitimate only when a real content difference forces them (verify by measurement, #3) — never an accident of not checking. Once sizes are content-fit-safe, THEN apply #4 (shared/round values, minimal distinct edges) on top. |
| 8 | aspect-locked at usage site | `aspect-locked` override at a usage site renders squashed (e.g. a 16×16 icon comes out 16×8) | `aspect-locked` only removes the *redundant* dimension when set on a part's OWN base box (single source of truth, like `atom/avatar.json`'s `aspect-locked, w:20`). Overriding an `extends` of a part whose base already bakes an explicit competing `h` (e.g. `cluster/dot`'s `h:8`) does NOT clear that baked value — dial merge only overwrites keys the override actually mentions (C8), so the old `h` still wins over the CSS-computed aspect-ratio height. Either fix it in the part's own base file, or override both `w` and `h` explicitly (no `aspect-locked` benefit at a usage site over an already-fixed part) — verify visually (`getBoundingClientRect`), don't assume. |
| 9 | Fill ≠ equal (resolved) | Multiple `fill` siblings in a row with *different* content don't come out equal width | **RESOLVED by #10** — `.bx-fill` was `flex:1 1 auto` (content-based basis); fixed at the source. Historically: equal `flex-grow` only added equal *extra* px on top of each item's own (different) basis, so final widths differed. |
| 10 | Fill's basis fixed | (root cause of #9) `fill`'s CSS implementation didn't match its own vocabulary concept | The vocabulary/spec define `fill` only as "take available space" — generic, doesn't mention per-sibling behavior. `flex-basis:auto` was `tokens.css`'s implementation choice, made by CSS default, never a deliberate decision — and it silently broke the concept for N `fill` siblings with differing content. Audited every existing multi-`fill` usage repo-wide (`chart` bars, `data-table`/`layout-grid` cells, `splitter` panes, `dimension-line` flanks) — all have equal/empty content, so none depended on the old behavior. Fixed in `ui/tokens.css`: `.bx-fill{flex:1 1 auto}` → `flex:1 1 0}`. Now `fill` means equal share among `fill` siblings, for any N, by construction — no more hand-picked matching `w:` numbers needed for #7's equal-width case. Single-trailing-filler case (#6) unaffected — one flexible item always eats 100% of leftover regardless of basis. |
| 11 | Align blocks stretch | A `fixed`-size sibling (no `fill`) doesn't stretch to match a `fill` sibling's height, even with no explicit `h` anywhere | An explicit `align` token on the ROW (e.g. `start`) sets `align-items` for *all* its children — only a child's own `fill` escapes it (`.bx-fill` sets `align-self:stretch`, which overrides the parent's `align-items`). A `fixed` child has no `align-self` override, so it falls back to whatever the parent's `align-items` says — `start` (`flex-start`) instead of the default `stretch`. Found while making a screen genuinely fill the viewport: `body`'s box had `row, start, fill` — the `start` was blocking the sidebar from stretching to the (now-variable) body height. Fix: don't put a non-`stretch` align token on a row/stack whose `fixed` children are meant to stretch — omit `align` entirely (default is stretch-like) unless you specifically want `fill` siblings to be the *only* ones stretching. |
| 12 | Disabled needs a stroke | A `disabled`/low-opacity element (icon, dot, placeholder) is nearly invisible — "looks like it's missing" | `state:disabled` → `.bx-disabled{opacity:.45}` compounds with a *fill-only* shape (no `stroke` dial set, so no border at all — `bare` and "no stroke token" render identically). A small tinted circle/box with zero border, faded to 45%, can drop below the point of being perceptible against the page background — reads as absent, not dimmed. Give any small/faded placeholder shape an explicit `hairline` (or `solid`) stroke so its *outline* stays legible even when its fill is muted — don't rely on fill-tint contrast alone under `disabled`. |
| 13 | Skin-coupled color is fragile | An icon/glyph goes invisible under a different visual skin, even though nothing about the icon itself changed | The icon's color was derived at mount time from a sibling/parent's `getComputedStyle(...).borderColor` — that's a *skin* choice, free to change independently of content legibility. Never mirror a content-foreground color off border-color; let content inherit `.bx`'s own `color:var(--text)` (dark/legible by construction, stable across skins) instead. |
| 14 | Skin palette needs real contrast | A skin's border/hairline color measures near-1:1 contrast against its own fill-tint backgrounds — the border/outline reads as invisible, not "subtle" | When tuning a new skin's border-related tokens, don't just eyeball "should look subtle" — compute contrast ratio against the actual `tint0..3` fills it will sit on and keep it clearly perceptible (same failure class as #12, via palette choice instead of `disabled` state). |
| 15 | Two-skin toggle: font swap reflows `hug` | Switching between two visual skins measurably resizes `hug` (fit-content) boxes and shifts everything around/after them | Any per-skin change to font-family (or any property `hug`'s fit-content depends on: font, line-height, padding, border-width) reflows every `hug` box by a different amount depending on its text content. If toggling skins must not move content, keep those properties identical across skins — vary only non-metric properties (color, background, shadow, outline). |
| 16 | Two-skin toggle: border ≠ outline for a guide | A "debug guide" shown only in one skin/state shifts every nested box's content on toggle, worse the deeper the nesting | `border` participates in box-model layout (shrinks the content-box, inflates `hug`'s fit-content) purely from being present, regardless of width. A guide meant to appear/disappear without affecting layout must use `outline` (+ negative `outline-offset` to sit inside) — outline never participates in box-model layout in any state. |
| 17 | `packed` centers nothing alone | A single child in a `row`/`stack` sits flush against the start edge instead of centered, even with `mid` set | `align` (`mid`) only centers the *cross* axis. Centering the *main* axis with exactly one child needs a `distribute` token other than `packed` (flex-start) — `evenly`/`around` both center a lone child (equivalent at N=1). `packed` is only correct once there's real start-aligned content to pack against (e.g. an icon+text row). |
| 18 | Elastic gap needs static children | A box given a growth-suffixed `gap` (`gap:2+`/`gap:2++`) renders its dynamically-appended children flush together with zero gap, instead of growing | The L2 elastic-gap mechanism (`ui/render.js`'s `gapSpacer`) interleaves spacer elements while walking `node.children` *at `render()` time*. A container whose real children are appended later via direct DOM `appendChild` (e.g. `ui/quiz.js`'s `answersEl` — rendered once with zero static children, rows added at runtime) has nothing to interleave spacers between, and — because a growth-suffixed `gap` also skips the plain CSS `gap` property (checklist's own elastic-gap design: CSS `gap` can't flex) — ends up with *no* spacing mechanism at all. Only give a container a growth-suffixed `gap` when its children are the static ones declared in its own JSON `children` array (verify via `hug`-vs-`fill` sizing too — checklist #17-style: a `hug` container also has zero excess by construction, so a growth suffix there is a silent no-op, not wrong but pointless). |
